# ADR 0005: Per-request token budget, recursion limit and LLM timeouts; hash-chained audit log

**Status:** accepted · 2026-08-03

## Backpressure: making the budget claim true

The deployment checklist told operators to rate-limit at the proxy because "the app enforces token/tool budgets". Only half of that was real. `MAX_TOOL_ROUNDS` bounds how many model calls a run makes but not how large they are — `read_article` returns every chunk of an article, so one round is unbounded in size. `usage_metadata` was never read anywhere in the repo, the graph ran on LangGraph's default recursion limit, and the OpenAI client ships with two retries and *no* timeout, so one hung call pinned a request and its DB session indefinitely.

Three bounds, all constants in `app/agent/graph.py` next to `MAX_TOOL_ROUNDS`:

- **`MAX_TOTAL_TOKENS` (80,000)** — summed from `usage_metadata.total_tokens` across every model call in the request: router, agent turns, finalize, grounding. `guard_input` resets the counter, so a new turn on an existing thread starts its own budget while a resumed approval keeps the running total (it is the same run).
- **`RECURSION_LIMIT` (`MAX_QA_SUPERSTEPS + 2`, i.e. 20)** — passed on the graph invocation in `app/api/chat.py`. It is a backstop, not a working limit: a maximal legitimate run (six tool rounds, then `finalize`) needs `MAX_QA_SUPERSTEPS` = `2 * MAX_TOOL_ROUNDS + 6` = **18** supersteps, and that 18 is measured rather than reasoned about — `tests/test_agent_budget.py::test_a_maximal_qa_run_needs_the_supersteps_claimed` runs one at exactly 18 and again at 17, where it must raise. Exceeding the limit raises `GraphRecursionError`, which `/chat` already surfaces as an SSE `error` event.
- **`LLM_TIMEOUT_SECONDS` (60)** and **`EMBEDDING_TIMEOUT_SECONDS` (60)** — per call, on both arms. The chat client and the embeddings client are separate OpenAI clients and each ships with no timeout; a hung embedding call sits inside `hybrid_search`, inside the tool node, holding the request's `AsyncSession` exactly as a hung chat call would. Retries stay at the OpenAI client default of two.

**Over budget ends the run, it does not truncate it.** `finalize` answers the *tool-round* budget by making one more model call with tools unbound — precisely what a blown *token* budget cannot afford. So `budget_exceeded` is a separate node that spends nothing: it fills every pending `tool_call_id` with a stub tool message (finalize's rule, because a dangling `tool_use` corrupts the next turn on the thread), appends a message saying the run stopped and at what cost, sets `grounded=False`, and routes straight to `END` — there is no answer for the grounding pass to audit.

## `grounded` fails closed, on every path that verified nothing

`budget_exceeded` was the only node that got this right. `guard_input`'s refusal branches set no verdict at all and `verify()` returned `grounded=True` outright when there were no citations to check, and both landed as `ragkit.grounded=true` on the run span and `"grounded": true` in the Art. 12 audit row. Since deployment.md tells operators to alert on `ragkit.grounded=false`, the effect was that an answer produced from **zero** retrieved sources — the run most likely to be hallucinated — was the one run the alert could never fire on. Same shape as the fail-open that commit 23786e0 closed in the verifier itself.

`guard_input` now seeds `grounded=False` for the whole run and every reader in `app/api/chat.py` defaults to `False` rather than `True`: the value is only ever raised by a check that actually ran. A refusal, a rejected draft, a stop at the token budget and an answer with no sources all report `grounded=false`, with `grounding_issues` saying which.

Rejected: making `grounded` tri-state (`grounded` / `ungrounded` / `unverified`). The distinction is real, but the boolean is a published contract — the SSE `grounding` event, `frontend/lib/types.ts`, the eval harness's digest — and every one of those consumers wants the same answer for both false cases: do not trust this. So the third value goes where it costs nothing and helps most, `gen_ai.evaluation.score.label` on the `node.verify` span, which an operator can already split on; the boolean stays a boolean and stays pessimistic.

Two limits worth stating plainly. The token budget is a loop bound: it is checked when the model asks for *more* tools, so a run overshoots by at most the response that crossed the line, and an answer that arrives already over budget still gets its one grounding call rather than shipping unverified. And a provider that reports no `usage_metadata` contributes 0 — with such a model the token budget enforces nothing and only the round and recursion bounds remain.

## Audit log: a hash chain, because "append-only" was a convention

`audit_log` was append-only only in the sense that the application exposes no update or delete route. That is not record-keeping evidence under AI Act Art. 12 — anyone with database credentials can edit a row and nothing shows. Each entry now carries `prev_hash` (the previous entry's `entry_hash`) and its own `entry_hash`: sha256 over `prev_hash` plus id, actor, action, resource, detail and timestamp. `GET /audit/verify` (admin) walks the chain and returns the first break with the entry id and whether the row failed its own hash (edited) or its link (deleted or reordered).

- **Chain order comes from the database.** `audit_log.seq` is a `bigserial` and the table's primary key; the writer links onto the tail by `seq DESC` and the verifier walks by `seq ASC`. The first cut of this ordered by `(created_at, id)` and shipped exactly the cry-wolf failure the advisory lock below exists to prevent: `created_at` is `datetime.now(UTC)` taken in the application, which is neither monotonic (an NTP correction steps it backwards) nor fine-grained enough to separate two appends on every platform, and `id` is a `uuid4`, which sorts at random against write order. Writer and verifier then disagreed about which row was last, and one inversion poisons `/audit/verify` from that row onward — on a log nobody had touched. `id` stays as the opaque public identifier (`broken_at`), now `UNIQUE` rather than the key.
- **Appends are serialized on a Postgres advisory transaction lock.** A sequence orders the rows; it does not stop two writers from reading the same tail and hashing onto it. A fork is indistinguishable from tampering when the chain is walked — tamper-evidence that cries wolf under ordinary concurrent traffic is worse than none. SQLite has no equivalent; the tests that run on it write from a single task.
- **Timestamps are canonicalised to aware UTC before hashing**, because SQLite drops `tzinfo` on the round trip and the value read back would otherwise hash differently from the value written.
- **The migration backfills the chain over existing rows.** They were never hashed at write time, so the backfill protects them from that point on and says nothing about whether they were altered before it ran. Without it `/audit/verify` would report a break at the first legacy row on every existing deployment, which is honest and useless. It numbers those rows by `(created_at, id)` — the only order that exists for data written before `seq` did — then hands the column to the sequence.
- **`/audit/verify` walks in pages** (`VERIFY_PAGE_SIZE`, 500 rows, each page expunged from the session). deployment.md asks operators to poll the endpoint and the log only grows; loading it whole through the ORM on the request path is an outage waiting on the audit trail's own success.
- **What the chain does not prove is documented, not papered over.** Deleting the newest rows leaves the remainder walking clean, and an unkeyed sha256 over public columns can be recomputed by anyone with `UPDATE` on the table. The table in docs/security.md states both, and `tests/test_audit_chain.py::test_truncating_the_newest_entries_is_not_detected` pins the first so the claim and the code cannot drift.

Rejected: a unique index on `prev_hash` (a fork becomes an IntegrityError, i.e. a 500 for an ordinary user — the advisory lock prevents the fork instead of failing the request); approximating tokens with tiktoken when a provider reports no usage (a guessed number enforcing a budget is worse than a stated gap); signing entries with an HMAC or KMS key, or anchoring the head hash in an append-only store outside the database (either would close the recompute and truncation gaps, and both cost key or infrastructure management this kit deliberately does not have — so they are written down as limitations instead).
